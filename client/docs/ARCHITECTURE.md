# Architecture

myAI is a static progressive web application. There is no application server component in this repository and no JavaScript build step.

## Shell

`index.html` is the UI shell. `sw.js` installs an explicit cache generation and excludes service/API routes from application caching. `src/js/version.js` asks the active service worker which shell is actually serving the page, so a stale cached page cannot claim a newer build merely because source files on disk changed.

A new build installs next to the one serving and waits (Build 129 and later). An open tab keeps the files of the build it started with, and loads nothing after it has started (its resampling worker starts with the page); the version badge offers the new build ("v129 › v130"), and tapping it asks the waiting worker to take over (`{type: 'activate-now'}`), waits for the controller to change and reloads. Every open tab of the app is then served by the new build and offers to reload into it; none is reloaded under its user. A new worker that replaces one of a build before 129 (an older `myai-shell-vN` cache) still takes over by itself, because those pages cannot ask. The shell is installed whole or not at all: every file is fetched, its body read at once into a response of its own (which also drops a redirect, since a navigation must not be answered with a redirected response), and only then stored. An install that fails is shown as failed ("Try installing v130 again") instead of "Installing v130..." for good. A page loaded past the worker (a hard reload) is never offered an older build, and lets its own, waiting build take over. Activation deletes only the shells of older builds, never one a newer build is installing. A navigation is answered from the shell only for the app's own page, the scope or `index.html` in it (Build 134); a navigation to any other page of the origin, a document served beside the app or another service under the same host, is left to the network, since the cached page opened there would look for its modules next to the wrong address.

## Browser runtime

The modules under `src/js/` are intentionally kept in one directory. Broad responsibilities are:

- capture and audio: `recorder.js`, `audio.js`, `audio-format.js`, `webm-duration.js`, `wake-lock.js`;
- durable local state: `db.js`, `idb-min.js`, `retention-core.js`, `backup-core.js`, `recording-lock.js`;
- transcription: `transcribe.js`, `transcribe-core.js`, `live-scribe.js`, `live-scribe-core.js`, `live-refine-core.js`;
- speaker/language processing: `diarize-core.js`, `speaker-infer-core.js`, `speaker-confirm-core.js`, `translate-core.js`;
- replies and automation: `reply.js`, `reply-core.js`, `auto-pipeline.js`, `jobs.js`;
- UI: `main.js`, `gui.js`, `row-state-core.js`, `settings.js`, `help.js`, `live-render.js`, `live-inline.js`, `live-tabs.js`, `player-core.js`, `clipboard-core.js`. `live-view.js` is kept on the server only for pop-ups of Build 128 tabs still open when a newer build is deployed; nothing of this build loads it.

## Local database

The current IndexedDB schema is version 13, which added the small `capture_beats` store for the recording heartbeat to version 12 without touching stored data. A schema-version change is additive: `applySchema` in `db-lifecycle-core.js` creates whatever stores and indexes of the current layout are missing and deletes nothing. There are no per-version row migrations, legacy-store readers, or boot-time data movers. A tab keeps its connection when a newer version asks for it while it is recording, saving a recording, running the automatic work a stopped recording starts, or running a transcription, reply or conversion; it gives the connection up by itself once none of that is left, so the newer version starts without anyone closing a tab and nothing the old tab started loses its result.

Audio and the recording row that owns it are written in one transaction (`commitAudio`), after the row has agreed to take it. A conversion or remux that finishes after its recording or audio was deleted therefore writes nothing, and startup sweeps any audio that no recording owns.

The current stores are `recordings`, `audio`, `audio_fragments`, `live_transcripts` and `capture_beats`. Large master audio lives in `audio`; recording rows contain lightweight metadata such as `audioBytes`.

A recording whose tab closed or crashed is recovered by any tab still open, not only after the next reload: soon after the other tab's lease disappears, and every minute in case nothing was noticed. At startup, live transcripts that no recording owns are found from their keys alone, since a live transcript can be megabytes.

## External services

Two same-origin proxy routes are configured in `src/js/config.js`: `/transcribe` for VTS and `/ollama` for an Ollama-compatible service. The service worker leaves these routes network-owned. One selected AI model is used for both replies and translation.

## Tests

`tests/baseline-contract.json` is the machine-readable compatibility contract. `tests/run-baseline.mjs` executes unit, static, integration and mutation suites, side by side where the machine has the cores for it (`tests/helpers/baseline-core.mjs` plans the order), and writes a generated report with each suite's time under `artifacts/`. The mutation guards are listed in `tests/mutation/guards.mjs` and run in parallel by `tests/mutation/mutation-smoke.mjs`. `tests/integration/journeys-integration.mjs` drives whole user journeys through the real page in Chromium, including a second build with only the database version raised, served from the same origin.

The journeys suite serves the tree at `/` and, under `/next/`, the same tree with only the database version raised, which is what the next schema-changing build looks like to a browser that already has data. It serves no service worker, so the two builds keep separate module graphs on one origin. Its stand-in for Ollama behaves like the real one where live translation depends on it: the model is loaded with one context size, a request for a different one reloads it, and a request that arrives during a reload waits for it; it starts with the model loaded at the context a long reply leaves. Each journey is named with `journey(...)`, and a failure says which journey it was in.

`tests/unit/saved-transcripts.test.mjs`, `tests/unit/storage-paths.test.mjs` and `tests/unit/app-behaviour.test.mjs` run the real `transcribe.js`, `reply.js`, `settings.js`, `recorder.js` and `db.js` under node. `tests/helpers/app-harness.mjs` gives them a page that records its dialogs and downloads, and one tab's Web Locks, and a module hook swaps the IndexedDB wrapper `idb-min.js` for `tests/fixtures/memory-idb.mjs`: stores with key paths and indexes, key ranges, cursors, transactions that commit whole or not at all and run one after another where they overlap, connections that a newer version asks to close (and that may refuse while busy), a log of every request, and failures or delays injected into chosen requests. The saved-transcripts suite answers with a stand-in transcription server that hears the audio it is sent: each utterance is a run of samples at its own level, so the server knows which utterances a chunk holds, where, and which ones the chunk's edge cut short.

`tests/integration/shell-update-integration.mjs` runs the service worker in Chromium, each scenario on an origin of its own: a new build waiting beside the one serving while another tab keeps its files, then taking over when asked; an install that fails and is tried again; a server that redirects `index.html`; and a worker replacing one of a build before 129.

The static-integrity suite reads source text. A guard that only it catches can pass while the behaviour it stands for is broken, so `tests/baseline-contract.json` records how many such guards there may be (`staticOnlyGuardCeiling`) and the contract suite fails when there are more, or fewer without the ceiling lowered with them: the number only goes down. Its checks find a function or block by its braces (`tests/helpers/source-blocks.mjs`) and a line break by `\n\s*`, so none of them depends on how the code is indented.

## Comments

What the code does is said by its names. Why it does it, when the reason is not obvious from the code (a threshold, an ordering that matters, a case that looks like a bug but is not), is said in a short comment next to the line it explains, where it is read and kept up to date together with that line. These documents describe how the parts fit together; they are not the place for the reason behind a single line. Build 127 removed every comment and had the static suite reject new ones; Build 128 dropped that rule, because a reason kept away from its line drifts from it.

## Live transcript evidence model

The live transcript is allowed to revise recent presentation when there is stronger evidence from the same audio, but it is not allowed to rewrite merely because text looks awkward. Adjacent-window repetition is first detected textually, then checked by retranscribing a wider region of the original in-memory PCM. A correction is accepted only when the wider pass strongly corroborates the same vocabulary while removing the suspected duplicate. Candidate languages are similarly evidence-gated before they become user-visible.

A live session is one run of live transcription. Every line key names the session it came from, and hiding and showing live transcription during a recording starts a new session that carries the lines, their translations, languages and speaker evidence across, so no key is ever reused for a different line. The copied transcript and the saved one are built from the same snapshot: every line from the beginning, including lines that scrolled out of view, without notices.

Live windows are released in order, so one window must not be able to hold back the rest. A window the server fails on while it answers other windows gets a strike each time; after two it is released as a gap, marked on the next line and noted in the transcript, and left to the transcription after the recording. A failure while nothing is answered is an outage and costs no window its place. Translation boxes queue the newest untranslated lines first and then work back through older ones, so every line is reachable; only the model's own answer (an empty reply, or a single line it cannot finish in time) counts against a line, never a server that is down. A language needs words to count: a window with none is no evidence, and the first language needs the same evidence as any other. A window that was heard and held nothing new is not a gap: only a window whose audio was dropped or left for later, or the first one after dropped audio, marks the next line. The window after dropped audio carries nothing from before the gap, so it cannot splice old words onto new ones.

Speaker labels are grouped in the browser from the voiceprints the server sends with each line (`diarize-core.js`). Every new line regroups the lines of the window, but a voice stays a voice (Build 132). A group becomes a voice once it has said two lines that sound like each other clearly more than like any other group (0.10), or three lines; the regrouping then starts from the lines already its own, a line of a voice moves to another voice only when it sounds clearly more like that one (0.15), and two voices become one only when every line of the smaller sounds more like the other than like the rest of its own, or both have said five lines and score 0.70 against each other. A named voice outlives an unnamed one, and two differently named voices are never joined. Lines that are not part of a voice group as before: a line starts a group of its own below 0.35 against every group, and such groups merge from 0.40. Numbers appear on every line, earlier ones included, once two voices have spoken, and stay for the rest of the session. A line whose group is not a voice carries the number before it, and the header counts it as a stray line. The 60% confidence is only shown in the header, as how sure the app is. The numbers on screen are not the identities the clustering keeps (Build 133): a group takes an identity before it is known to be a voice, most such groups never become one, and identities are never reused. Numbers are handed out when they first appear: the first two voices take 1 and 2 in the order they first spoke, each later voice takes the next number, and no number already on screen changes for a newcomer. When two voices become one, the joined voice keeps the lower number and the voices after it move up one, so the numbers on screen never skip one. The header, receipts, inference notes and suggestions use the same numbers; a suggestion keeps the number it was announced with, which is the number "confirm speaker N" names.

What the live transcript never heard (a window the server kept failing on, audio dropped while the server fell behind, windows still unsent at Stop, the part of a recovered recording after its last saved live transcript) is marked `[not transcribed live]` where it was when the live transcript is saved as the recording's transcript, and the number of such holes is stored on it (`holes`, Build 134). Such a recording's row offers 📝 Fill gaps, also in the compact list, which transcribes only those parts and saves a reading made from the live lines and them; the offer ends once a reading made after the recording exists. With Auto-transcribe on, the pass after the recording fills them by itself. The live notes say which of the two will happen, so a note never promises a transcription after the recording that will not run.

Speaker names inferred from conversation are suggestions only. A suggestion is applied only after the spoken confirmation `confirm speaker N`; the removed numbered command system has no runtime module or documentation path.

## Work after a recording

A stopped recording starts its automatic transcription and reply, then the cleanup pass, one after another (`runAfterRecording`). A step that was cancelled, by ✕ or by deleting the recording, ends the chain; a step that failed is reported and the next still runs. Transcription and reply jobs exist from their first moment, so a cancel that arrives while they are still reading is not lost. The translation fill that completes the other languages of a live transcript shares the AI model with replies: it waits while any reply is running, tries a batch the server did not answer once more at the end, and reports a stop in a notice of its own (`fillError`) rather than as a failed automatic step. A cleanup pass set to replace the live reading also removes the live transcript that reading was made from, unless a reply was written from it; nothing on screen would show it any more.

## Staying fast on long recordings

The transcription after a recording sends two chunks at a time to start, one more after each quick answer up to ten, one fewer after an answer slow enough to show that requests are queuing at the server, and half as many after a timeout or a busy answer (503 or 429); a chunk that timed out is sent again only after a longer wait, since the server is usually still working on it. A chunk turned away as busy while another chunk of the same transcription is at the server waits for that one to come back and then asks again, without using up one of its tries (Build 134): the server is alive and busy with this transcription's own work, and the pauses between tries can be shorter than the time it takes for a chunk. An answer wakes a waiting chunk; another refusal does not, unless it was the last of the transcription's chunks at the server, since then nothing of its own will come back to wake it; and a chunk stops waiting after twenty such turns. A busy answer with none of this transcription's chunks at the server means the server is busy with something else, and the chunk is retried after the usual pauses. Speaker clustering keeps a running sum per speaker and clusters the lines of one live window together.

While recording, the live transcript is saved when it has changed and either five minutes have passed, or a minute has passed and it grew by a quarter or by 4,000 characters since the last save; the heartbeat decides this from the transcript's size and a signature of its lines, translations and coverage, without building it. A live window waiting in the offline queue holds the WAV it will send and, for the repeated-words review, its 16 kHz samples; windows waiting behind the newest two let the samples go, and every window counts what it holds, so the queue's byte cap is the memory it uses.

A pop-up view is a page with no script of its own and a policy that allows none: the tab that opened it draws into it with the same renderer as the inline view, on the pop-up's own animation frames, and posts it nothing, so what it shows cannot reach a page the window was later navigated to. Where the opening tab may not read the pop-up (a browser that gives it an origin of its own), the pop-up is closed and the view opens in the page.

The viewers do their work once per frame where the page has frames, so a burst of messages, such as the whole history replayed when a viewer opens, costs one layout; a window that gets no frames, like a popup behind the app, is written on a timer instead. The transcription log viewer renders each chunk once, trimmed against the text before it, and again only the chunks after it whose starting text changed; a chunk sent again with a different start moves, and the log is rendered whole once more. The reply viewer gathers the tokens of a frame and appends them to a few text nodes that grow. Showing 📝 again during a recording keeps the rows already on screen.

A reply that needs a larger context than the model is normally loaded with makes the server reload the model inside that request, and a long prompt takes longer to read, so its first word gets 3 minutes instead of the usual wait.

## The recordings list

A repaint of the list moves the audio being listened to, and a title being typed, into the rebuilt rows: playback neither stops nor rewinds, and the half-typed title stays focused without being saved. A transcription or reply whose row was rebuilt while it ran repaints the row on screen when it ends, so its button is usable again. A key already handled by a transcript preview or a context title opens its view once, and Tab and Shift+Tab go round inside an open dialog, also when the focus is on the dialog itself. A preview takes Enter and Space only when they are pressed on the preview itself; on the 📋 inside it they press the 📋 (Build 134). A title with no spaces in it, and the text of a warning, wrap inside the row instead of widening the page on a phone.

## Clipboard context

`clipboard-core.js` turns clipboard text into a context item and nothing more. It has no storage of its own: the item joins `contextChain`, which already decides how context is displayed, fed to the model, exported, retained and deleted. The module is pure, so what a paste becomes is decided without a clipboard, a DOM or a database.

## Silence is evidence, not failure

A transcription chunk that fails is retried on a bounded schedule before it is recorded as a hole. When a chunk still yields nothing, the client judges the core of the audio it sent, the minute that chunk answers for, without the overlap it shares with its neighbours: a core whose measured peak and RMS are both below the silence thresholds is reported as no speech detected, and one that carried sound is reported as unavailable. Words spoken just after a quiet minute therefore do not make that minute count as sound. Consecutive placeholders of the same kind collapse into the single span they cover, so a quiet half-hour reads as one note rather than thirty. A recording that is entirely silence is a transcript that says so, not a transcription failure.

## Putting a transcript together

Every window that is sent to the server, a chunk after the recording or a live window, hears some audio its neighbour also heard, and the server may repeat those words. Which segments a window owns: a chunk after the recording overlaps its neighbours on both sides, so a segment belongs to the chunk its middle falls in; a live window has only the carry before its core and nothing after it, so it also keeps a sentence that began in the carry and runs on into its core, and the live seam trim removes the words the previous window already heard. A sentence runs on when it reaches well into the core (0.3 s), or, however briefly it reaches in, when the audio there has sound (at least half the level of the whole sentence); one that only touches a quiet core is the previous window's words heard again. When the server placed every word outside a core that was quiet, those words are the neighbour's and are saved by it at their real time; when the core had about as much sound as the place the server named, the timestamps do not match the audio and the server's text is used for the core rather than losing that stretch. A server that gives no timed segments at all has its text used, trimmed at the overlaps.

A window edge can cut a word in two, and the two windows then read it differently: the window after a seam may hear only the end of the seam's first word ("day" for "today"), the window before it only the start of its last ("after" for "afternoon"), and the clipped side may come out as another word ("yeah" for "year"). The seam trim (`seamTrim` in `dedup.js`) takes such an edge word as the same word when the two readings agree on the part both windows heard, its end where the seam opens and its start where it closes, as a whole fragment of two letters or more or a shared part of three letters or more; a shared part of digits only does not count, since 2023 and 2024 are different numbers. A seam of four words or more may also have one misheard word in every four, as before; a seam of two or three words may have one cut edge word and no other difference. Where the seam closes on a cut word, the next window's reading of it is kept, since that window heard it whole (Build 134).

When the saved transcript is assembled (`reassembleTimeline`), a line is trimmed only against words another window heard at the same time (within a quarter of a second), never against the line before it in its own window: "Okay." followed by "Okay, so we start." is two things said, not one heard twice. The lines of the live transcript were already reconciled window by window while they were recorded, so they are saved as the live view showed them and are only trimmed where a chunk transcribed after the recording meets them. A saved live line carries its speaker in front of its words ("Speaker 1: ...") and, from Build 134, also on its own (`speakerLabel`): the trim works on the words, which another window may have heard too, and the speaker is put back in front of what is kept. Backfilled lines follow the same rule where two backfill windows overlap.

## Audio at 16 kHz

The transcription server takes 16 kHz mono. PCM (live windows, WAV recordings, a range of a WAV for one chunk) is converted by `resample-core.js`, a Kaiser-windowed sinc low-pass just below 8 kHz read through a polyphase table, in a worker (`resample-worker.js`) so a long recording does not hold up the page; where no worker starts, the page does it a second of audio at a time. A WAV recording is converted a chunk at a time as it is transcribed, each chunk read with the frames around it so its edges are filtered like the rest of it. Measured in Chromium, the conversion it replaced (an AudioBufferSourceNode played into a 16 kHz OfflineAudioContext) passed every tone above 8 kHz straight through as an alias at full level: a 12 kHz tone in 48 kHz audio came out as a 4 kHz tone at 0 dB. The resampler keeps 0 to 6 kHz flat, is 1.4 dB down at 6.8 kHz, holds tones from 9 to 20 kHz 79 to 104 dB down, and is still closing between 8 and 9 kHz (8.1 kHz is 50 dB down, 8.8 kHz 78). Compressed recordings are decoded by `decodeAudioData` on a 16 kHz context, which resamples as it decodes through the browser's own band-limited resampler.

## Automatic gain

The recorder steers a gain node ahead of the limiter by the level of what it hears, read as floats every 100 ms (`meterLevel`, `nextAutoGain` in `capture-health-core.js`), towards 0.15 RMS between 0.05x and 24x. Below -66 dBFS it leaves the gain alone, so a pause is not turned up to the cap. A byte reading could not see that: the spec rounds bytes down, and any real noise reads about 0.0055 RMS. The limiter's settings (`LIMITER_SETTINGS`) lie inside the ranges Web Audio accepts; Build 133 asked for a ratio of 30, which every browser clamps to 20 with a console warning on each recording.

## Audio-backed transcript review

The transcript pipeline treats an ASR result as an observation of the audio, not as an immutable fact. A bounded reviewer handles one damaging inconsistency: adjacent transcript lines whose timestamps overlap while their text repeats the same phrase. It retranscribes the suspicious audio and accepts the second pass only when it keeps the surrounding vocabulary while removing the echo; otherwise the first transcript stays. The same holds before a recording's transcript is saved: live lines set aside for a replay come back when the replay fails or hears no words.

Live windows overlap by two seconds, so only a line that starts inside that overlap can repeat words the previous window already produced; only such a line is trimmed against the text before it, and a line never starts earlier than the line before it, so the saved order is the spoken order.
